# Phase Research: Bayesian-Bootstrap RNG Draw Accounting (port `YetiRankTreeSeeder`-style per-candidate accounting into the generic boosting loop)

## Research Summary

- **Phase goal:** fix the `#[ignore]`d tree-1+ divergence in `bootstrap_oracle_bayesian` (and the related `regularization_oracle_bagging_temp` / `regularization_oracle_random_strength`) by replacing the flat `depth + POST_TREE_EXTRA_DRAWS` bulk RNG advance in `crates/cb-train/src/boosting.rs` with a real per-candidate draw model, mirroring `YetiRankTreeSeeder`.
- **Recommended-approach inputs verified:** `feature_borders: &[Vec<f64>]` (the exact list `yetirank_n_candidate_features = feature_borders.len()` already uses) is in scope everywhere in `train_inner` — including at the bulk-advance call site — so the candidate count is already available with no new plumbing. `[CODEGRAPH: boosting.rs train_inner 2259-4757]`
- **Most important constraint verified:** `YetiRankTreeSeeder` **owns** its `TFastRng64` (`rng: TFastRng64` field, seeded fresh in `new_with_scoring`) — it does **not** take a `&mut TFastRng64`. It therefore runs on a **separate, independent RNG stream** from the shared `rng` variable in `train_inner` that also drives `bootstrap()`. "Porting" cannot mean literally reusing the struct as-is against the shared stream; either the draw *logic* must be re-implemented inline against the shared `rng`, or `YetiRankTreeSeeder` must be refactored to borrow an external `&mut TFastRng64`. `[CODEGRAPH: yetirank.rs:262-320]`
- **Highest-risk finding (regression):** `bootstrap_oracle_bernoulli` and `bootstrap_oracle_mvs` (and `regularization_oracle_l2`) currently **pass bit-exact** using the *same* flat `depth+1` bulk model, on fixtures with the *same* candidate-feature shape (4 float features, one with **zero borders** — an "unused-but-quantized" candidate) that the ignored Bayesian scenario also has. If the true required draw count differs from `depth+1`, Bernoulli/MVS should show the same kind of divergence Bayesian does — yet they don't. This is not fully explained by the evidence gathered here and must be resolved (or the fix scoped away from Bernoulli/MVS) before changing the bulk-advance formula, because a "more correct" per-candidate model could newly break two currently-green oracle tests. See Open Questions.
- **Second load-bearing finding:** the WR-02 fix already applied to `YetiRankTreeSeeder` (count *every* listed float feature, including empty-border ones, as an RNG-consuming candidate) is **not** mirrored in the perturbed (`random_strength != 0`) plain-grower path (`tree.rs::select_level_perturbed`), which explicitly **skips** border-less features (`if borders.is_empty() { feature_best.push(None); continue; }` — no draw). The same fixtures that exercise the ignored Bayesian bulk-advance bug also have a border-less feature and feed the *also*-ignored `regularization_oracle_random_strength` test, suggesting a structurally related (but not necessarily identical) gap in the perturbed path.

## Phase Requirements

### In Scope
- Replace/augment the `else if draws_active { for _ in 0..(params.depth + POST_TREE_EXTRA_DRAWS) { rng.gen_rand(); } }` branch (`crates/cb-train/src/boosting.rs:4571-4575`) with a per-candidate-feature draw model derived from `feature_borders.len()` (mirroring `yetirank_n_candidate_features`, `boosting.rs:2459`), so `bootstrap_oracle_bayesian` (currently `#[ignore]`d, `crates/cb-train/tests/bootstrap_oracle_test.rs:165-169`) can be un-ignored.
- By construction this also touches every other `draws_active && !perturb_active` scenario: `bootstrap_oracle_bernoulli`, `bootstrap_oracle_mvs`, `bootstrap_oracle_no` (no-op, `draws_active=false`), and `regularization_oracle_bagging_temp` (`#[ignore]`d, same TRAIN-04 residual per its own comment, `crates/cb-train/tests/regularization_oracle_test.rs:334-347`).

### Acceptance Criteria (inferred from the failing/ignored tests — not independently specified anywhere in the repo)
- `cargo test -p cb-train --test bootstrap_oracle_test -- --include-ignored` must pass all 5 tests (currently 4 passed / 1 failed when forced to run, see Testing section) with the `#[ignore]` attribute removed from `bootstrap_oracle_bayesian`.
- `regularization_oracle_bagging_temp` (`crates/cb-train/tests/regularization_oracle_test.rs:339`) should also newly pass if it shares the same root cause (unverified — see Open Questions).
- No regression in any currently-green oracle test enumerated in "Project Impact Scope" below, most importantly `bootstrap_oracle_bernoulli` / `bootstrap_oracle_mvs`.

### Out of Scope
- `regularization_oracle_random_strength` (`#[ignore]`d, perturb_active=true path, `crates/cb-train/tests/regularization_oracle_test.rs:305-315`) is a **different code path** (`tree.rs::select_level_perturbed`, which already does real per-candidate `SelectBestCandidate` draws on the main RNG). The task as given targets the **non-perturbed** (`perturb_active=false`) bulk-advance branch only. Whether the same fix should also touch `select_level_perturbed`'s border-less-feature skip is a related-but-separate decision the planner must make explicitly (see Open Questions) — do not silently fold it in.
- The device/GPU bootstrap kernels (`crates/cb-backend/src/kernels/bootstrap_device.rs`, `DeviceBootstrapKind::{Bernoulli,Bayesian,Poisson}`) are **structurally unreachable** for any `bootstrap_type != No` fit today (see Impact Scope) — out of scope, no interaction.
- CTR-aware training (`has_ctr` dispatch) is out of scope for the bulk-advance fix itself (the target fixture has zero CTR features), but the planner must still decide whether the new per-candidate formula should read the CTR candidate count too, for future-proofing — see Open Questions.

### Open or Conflicting Requirements
- The task background states the root-cause hypothesis as settled fact ("the boosting loop does NOT perform real per-candidate RNG draws... substitutes a flat bulk advance... an approximation that could not be verified against C++ instrumentation"). Verification here **confirms the code and comments say exactly this**, but the empirical pass/fail pattern of the existing tests (Bernoulli/MVS pass, only Bayesian+bagging_temp fail, on identically-shaped candidate sets) is in tension with "the flat model is simply wrong and a corrected model will fix everything." See Open Questions — this must be resolved analytically or via new instrumentation before implementation, not assumed.

## Current Project Architecture

### Relevant subsystems and boundaries
- `crates/cb-train/src/boosting.rs` — `train_inner<R: Runtime>` (2259-4757) is the single monolithic per-iteration boosting loop. All entry points (`train`, `train_with_eval`, `train_with_eval_sets`, `train_ranking`, `train_cat`) funnel into it (`boosting.rs:1946-2168`). `feature_borders: &[Vec<f64>]` is a parameter threaded through every entry point and is in scope for the ENTIRE function body, including the bulk-advance site at the bottom. `[CODEGRAPH: boosting.rs 1946-2271]`
- `crates/cb-train/src/yetirank.rs` — `YetiRankTreeSeeder` (262-431): a hand-transcribed per-tree draw simulator for YetiRank/YetiRankPairwise/StochasticRank, owning its own `TFastRng64`.
- `crates/cb-train/src/bootstrap.rs` — `bootstrap()` (383-439): the `EBootstrapType` dispatch (`No`/`Bayesian`/`Bernoulli`/`Mvs`/`Poisson`), taking `rng: &mut TFastRng64` **by reference** — this is the SAME `cb_core::TFastRng64` type `boosting.rs`'s shared `rng` variable and `yetirank.rs`'s seeder both use, confirming a single-stream-per-fit RNG discipline is architecturally possible (bootstrap already takes `&mut`), even though `YetiRankTreeSeeder` currently does not use it that way.
- `crates/cb-train/src/tree.rs` — `Perturbation<'a>` (538-546, borrows `rng: &'a mut TFastRng64`) and `select_level_perturbed` (1041-1192): the REAL per-candidate draw implementation used when `random_strength != 0`.
- `crates/cb-backend/src/kernels/bootstrap_device.rs` — a parallel GPU bootstrap kernel family (`DeviceBootstrapKind::{Bernoulli,Bayesian,Poisson}`), gated entirely off by `device_host_eligible` (see Impact Scope) — never invoked from `train_inner`'s main dispatch when `bootstrap_type != No`.

### Existing data/control flow (verified against current file:line, not the task background's possibly-drifted numbers)
1. `train_inner` builds a single persistent `rng = TFastRng64::from_seed(params.random_seed)` (`boosting.rs:3011`), computes `perturb_active = params.random_strength != 0.0` and `draws_active = !matches!(bootstrap_type, No) || perturb_active` (`boosting.rs:3017-3018`).
2. Per tree, BEFORE bootstrap: `if draws_active { for _ in 0..PRE_TREE_DRAWS { rng.gen_rand(); } }` where `PRE_TREE_DRAWS: usize = 2` (`boosting.rs:58`, consumed at `3664-3668`).
3. `bootstrap(params.bootstrap_type, &der_obj, params.subsample, params.bagging_temperature, prev_leaf_mean_l2, &mut rng)` runs once per tree (`boosting.rs:3696-3703`), reading/advancing the SAME `rng`.
4. Tree growth dispatches on `grow_policy` / `is_pairwise_scoring` / `has_ctr` (`boosting.rs:3838-3936`). The plain oblivious `SymmetricTree` non-pairwise non-CTR arm is `greedy_tensor_search_oblivious_perturbed(... perturb.as_mut() ...)` (constructed at `boosting.rs:3800-3814`: `Some(Perturbation{rng:&mut rng, score_st_dev})` iff `perturb_active`, else `None`).
5. AFTER the tree is grown: the target bulk-advance branch, `boosting.rs:4548-4575`:
   ```rust
   if perturb_active {
       for _ in 0..POST_TREE_EXTRA_DRAWS { rng.gen_rand(); }   // POST_TREE_EXTRA_DRAWS = 1 (boosting.rs:65)
   } else if draws_active {
       for _ in 0..(params.depth + POST_TREE_EXTRA_DRAWS) { rng.gen_rand(); }
   }
   ```
   This is the code the phase must change. It is documented (comment directly above, `4548-4566`) as approximating ONLY two draw sources: `CalcScores`'s one `Rand.GenRand()` per level (`depth` draws) plus ONE leaf-estimation-seed draw per tree — it does **not** mention or account for any `SelectBestCandidate` per-candidate normal draws or Rsm-selection draws at `random_strength == 0`.
6. The `is_yetirank`/`is_stochasticrank` dispatch (`boosting.rs:2404-2506`) constructs `yetirank_seeder`/`stochasticrank_seeder` as `Option<YetiRankTreeSeeder>`, each owning an **independent** `TFastRng64::from_seed(params.random_seed)` — NOT the shared `rng` above. In every existing yetirank/stochasticrank oracle test, `random_strength: 0.0` and `bootstrap_type: EBootstrapType::No` are both pinned (`yetirank_oracle_test.rs:121,124`; `stochasticrank_oracle_test.rs:188,193`), so `draws_active = false` and the shared `rng`/bulk-advance branch never executes for those tests — the two RNG streams have never been exercised together and their interaction (if `bootstrap_type != No` were ever combined with a ranking loss) is untested.

### Existing reusable implementations
- `YetiRankTreeSeeder::next_tree` (`yetirank.rs:334-430`) — the per-level loop at `366-386` is the exact candidate-accounting algorithm the background references:
  ```rust
  for _level in 0..self.depth {
      for _ in 0..self.n_features { let _ = self.rng.gen_rand_real1(); }   // Rsm selection draw
      let _ = self.rng.gen_rand();                                        // CalcScores per-level seed
      for _ in 0..self.n_features { let _ = std_normal(&mut self.rng); }   // SelectBestCandidate normal, one per candidate
  }
  ```
  `self.n_features = yetirank_n_candidate_features = feature_borders.len()` (`boosting.rs:2459`), i.e. **every listed float feature, including ones with zero selected borders** (the WR-02 fix, `boosting.rs:2441-2458`).
- `cb_core::std_normal` — the exact Marsaglia-polar Box-Muller implementation already used by both `yetirank.rs:384` and `tree.rs`'s `random_score_instance` (via `cb_compute::score.rs:363`), so a shared, already-parity-verified normal-draw primitive exists and must be reused (not reimplemented).
- `tree.rs::select_level_perturbed` (1041-1192) — the ALREADY-shipped real per-candidate-feature draw sequence for `perturb_active=true`: step (1) one `rng.gen_rand()` per level (`CalcScores`), step (3) one `random_score_instance(..., &mut perturb.rng)` (== one `std_normal` draw) per candidate FEATURE with a non-empty border list, on the MAIN rng. This is architecturally the closest existing analogue to what the bulk-advance branch needs to reproduce for the `perturb_active=false` case (draw the same normals, discard the value) — **except** it currently has NO Rsm-selection draw and it SKIPS border-less features (diverging from the WR-02-fixed yetirank accounting).

### Current conventions and patterns
- Every RNG-consuming helper takes `rng: &mut TFastRng64` (bootstrap.rs, tree.rs's `Perturbation`) except `YetiRankTreeSeeder`, which is the one outlier that owns its stream.
- Draw-order fidelity is treated as load-bearing everywhere (f32 vs f64 width, Marsaglia-polar rejection counts, block-reseed offsets) — see `bootstrap.rs`'s `bayesian_weight`/`fast_logf` comments and `yetirank.rs`'s f32-accumulation comments.

## Recommended Architecture and Implementation Pattern

Not prescribed here per the task instructions (research only). Verified facts the planner needs to choose an approach:
- `feature_borders.len()` is already in scope at the bulk-advance site (`boosting.rs:4567-4575`) with no new parameter plumbing required — it is the same `train_inner` function parameter used at `2459` for `yetirank_n_candidate_features`.

## Spike Addendum (2026-07-29, post-research analytical spike)

Per user decision, an in-repo analytical spike (no C++ rebuild) was run to resolve Open Question #1 before writing SPEC/PLAN. Both temporary diagnostic changes were reverted; nothing below is committed.

1. **Brute-force post-tree draw-count sweep**: added a temporary env-gated override for the `depth + POST_TREE_EXTRA_DRAWS` bulk advance (`boosting.rs:4571-4575`) and swept integer replacement values 0-300 against the Bayesian fixture's tree-1 (index 1, 0-based) first split border. Found multiple exact matches (e.g. K=7, 17, 32, 36, 80, 153, ...), proving the divergence **is** main-RNG-phase-sensitive — the prior doc-comment's "INSENSITIVE to phase" claim was wrong. However:
   - The **same constant does not carry** to the tree-1→tree-2 gap: re-running the full 3-tree oracle test with K=7 fixes tree-1 completely (both splits match) but newly diverges at tree-2 (index 4). No single fixed K satisfies all tree gaps simultaneously.
   - Given the small number of distinct reachable split-border values near this candidate (multiple far-apart K values landed on the exact same bit-pattern), single-split-border exact matches are not fully reliable evidence of a "correct" phase — likely partly coincidental (low-cardinality outcome space).
2. **Theoretically-motivated fix attempt**: widened `perturb_active` to `draws_active` at the `Perturbation` construction site (`boosting.rs:3800`), with `score_st_dev = 0.0` when `random_strength == 0`, so the tree-growing search unconditionally runs the REAL per-candidate `random_score_instance`/`std_normal` draw (Marsaglia-polar, variable-length, matching upstream's confirmed-unconditional `GetInstance` call) instead of a bulk guess; removed the redundant bulk branch. Verified via `rng.call_count()` diagnostics that this genuinely changes the draw count (e.g. tree-0's grow went from 0 draws to 18 draws for the Bayesian fixture, vs. the ~7 the isolated single-axis sweep implied was needed). Result: **`bootstrap_oracle_bayesian` still fails** (same diff magnitude), **and `bootstrap_oracle_bernoulli`/`bootstrap_oracle_mvs` newly fail** (previously green). This is strong evidence that:
   - The true upstream draw count for the plain (non-ranking) dispatch is not simply "one real per-candidate draw per non-empty-border feature per level" either — the theoretically-correct-looking mechanism over-shoots substantially (18 vs. ~7 implied-needed).
   - Bernoulli/MVS's current green status is fragile/coincidental to the EXACT current constant, not evidence that `depth+1` is correct in a principled sense.
3. **Conclusion**: the root cause remains genuine RNG-phase drift in the shared bulk-advance branch, but neither a swept fixed constant nor the seemingly-correct per-candidate-replay generalization reproduces upstream's true behavior for this scenario. Resolving it conclusively requires real `CB_INSTRUMENT_LOG` ground truth from an upstream C++ build run against this exact plain-dispatch scenario (not the YetiRankPairwise-specific trace already committed, which does not necessarily transfer to the non-ranking dispatch).
4. **Decision**: per explicit user choice (AskUserQuestion, 2026-07-29), the chain was stopped here rather than committing to that C++ rebuild. No code fix was made; `bootstrap_oracle_bayesian` remains `#[ignore]`d. The misleading "structural Bayesian-specific" / "insensitive to phase" framing in `bootstrap_oracle_test.rs`'s doc-comment and the stale `SUMMARY`/`D-11` citation in `boosting.rs` were corrected to reflect these findings, so a future session does not re-derive or re-attempt the same dead ends.
