## 5. Deviations

1. **`X_cat.npy` is 1-D `[64] int32`, not `[64,1]`.** T06 inherits the combo generator,
   whose `X_cat` is `(64,2)` because it has two cat columns; with `CARDS=(6,)` the
   single-column convention of `ctr_device_mixed/` (`(64,) int32`) applies, and that is
   also literally what T05's Red block specifies (`X_cat.npy [64] int32`). The smoke test
   asserts `Array1<i32>` of length 64.
2. **The `catboost_info/` training-log directory emitted by the fit was deleted.** T06's
   Files line enumerates exactly eight fixture files; `ctr_device_combo/` happens to have
   its log dir committed, but that is log noise, not a fixture artifact. Nothing reads it.
3. **Two guards added beyond T06's three.** (a) every CTR descriptor must be `Counter`
   (the recipe has a single Counter `simple_ctr` and empty `combinations_ctr`, so any
   other type means recipe drift); (b) each Counter descriptor's serialized prior must be
   `0.5/1`. Both tighten the explicit-prior pin T06 calls THE trap; neither weakens
   anything.
4. **Corpus-contamination check.** It passed at generation time. Re-running the generator
   now would report the sibling `ctr_device_buckets/` and `ctr_device_btmv/` directories
   (created concurrently by the T05/T07 agents) as "offenders" — that is an artifact of
   wave-parallel execution, not contamination by this generator. The check was kept
   verbatim per T05.

## 6. FINDING for T12 (Counter e2e) — read before writing the e2e prior assertion

Measured on this fixture's data with upstream `catboost==1.2.10`:

```
simple_ctr=["Counter:Prior=0.5"] -> descriptor prior 0.5/1, ctr border 8.999999046325684
simple_ctr=["Counter"]           -> descriptor prior 0/1,   ctr border 8.999999046325684
simple_ctr=["Counter:Prior=3"]   -> descriptor prior 3/1,   ctr border 3.9999990463256836
max|Δ prediction| between all three arms = 0.0 (bit-identical)
```

⇒ **On the upstream side the Counter prior is prediction-neutral here**: upstream shifts
the CTR border to compensate, and with 16 CTR buckets over integer counts the shifted
value never crosses a bin boundary. Consequences for T12:

- The ≤1e-5 e2e comparison **cannot** be relied on to detect a Rust-side prior mismatch on
  this fixture. The explicit pin on both sides (`Counter:Prior=0.5` here, asserted by the
  smoke test; `simple_ctr_priors = vec![0.5]` in T12's `BoostParams`) is the guard — it is
  a construction-time contract, not something the fixture's predictions will police.
- This is an *upstream-side* measurement. If the Rust CTR border computation does **not**
  compensate the prior the same way, a mismatch would surface as a real divergence. Either
  way, T12 must set the prior explicitly and must not treat "e2e passes" as evidence that
  the prior matches.
