## 1. The design choice, settled IN WRITING BEFORE the first test line

The coordinator's consolidated T10 §2 + T16 finding, T18's and T19's notes were all read
first. The choice, and its reason, were written into the test file's module doc **before**
the file was first run — they are not a post-hoc rationalisation of a red test.

**(a) The comparison surface is the chosen-split IDENTITY sequence, not predictions.**
Per tree: `splits` (`Vec<Split>`), `ctr_splits` compared on the full `CtrSplitSpec` identity
`assign_leaf_over_ctr_columns` keys on — `(projection, ctr_type, prior_num, prior_denom,
target_border_idx, border)`, with `shift`/`scale` deliberately excluded as prior-derived —
`one_hot_splits`, and the per-level kind sequence; plus leaf values at ε = 1e-4 (D-07).
Predictions are excluded because they cannot detect a routing defect on **either**
non-Borders arm: Buckets' mirrored `b=0`/`b=1` columns at `Prior = 0.5` (T10 §2) and BTMV's
binclf `Sum == N[1]` identity with `Borders@0` (T15/T16).

**(b) A cindex-column-level differential was considered and rejected as unreachable, with
the reason recorded.** The coordinator's preferred option is a cindex-column comparison. The
device's CTR cindex columns are built inside `cb-backend`'s session
(`build_ctr_cindex_columns`) with no readback seam visible to a `cb-train` integration test,
and the CPU's live inside `boosting.rs`'s materializer; reaching them would require **new
production seams**, which T22's task text forbids ("Production files: none expected"). The
cindex-level evidence therefore stays where it already is — T08/T11/T14/T15's kernel
self-oracles, including T15's `btmv_and_borders_emit_identical_bins_at_binclf`. This is
stated in the test's module doc under "What this file honestly CANNOT say".

**(c) The Buckets arm therefore takes the coordinator's SECOND option: a prior ≠ 0.5.**
`combinations_ctr_priors = [0.25]`. At `Prior = 0.5`,
`ctr(b0) + ctr(b1) = (total + 1)/(total + 1) = 1` exactly, so the two Buckets columns of a
`(projection, prior)` pair binarize to mirrored bins, score **exactly** equal, and the winner
is decided by enumeration order — a raw sequence comparison would then diverge for a benign
reason, and an agreement would be uninformative. At `Prior = 0.25` the sum is
`(total + 0.5)/(total + 1)`, which is total-dependent, so the exact algebraic mirror is gone.

**Counter and BTMV keep `Prior = 0.5`** (the task text's value): `target_border_count(2)` is
`1` for both (`ctr/mod.rs`), so each `(projection, prior)` yields exactly ONE column and there
is no mirrored twin to tie with — the T10 §2 degeneracy is structurally absent, not merely
unobserved.

**(d) Honest limitation of (c), discovered later and recorded rather than hidden.** A prior
≠ 0.5 removes the exact-mirror IDENTITY but **not** the ordinal anti-monotonicity
(`bin(b0) + bin(b1) ≈ const`) that produces score ties between the two columns. At a longer
horizon the Buckets arm does hit such a tie — see `T22-OBS-2` (§5.2). The shipped arm is
below it; the limitation is written into the note and carried to the coordinator. No
assertion was weakened.

**(e) The CPU arm is genuinely the CPU grower, and that is asserted, not assumed.**
`CpuRefRuntime` overrides **only** `compute_gradients`, forwarding to a real `GpuBackend` so
both arms consume bit-identical derivatives and the differential isolates the GROWER. Every
device-seam method inherits the `cb_compute::Runtime` trait default (`begin → Ok(false)`,
`grow → Ok(None)`), the `device_nonsym_fit_test.rs:105-119` precedent. It is then wrapped in
`CountingCpu` (the `CountingGpu` shape, `inner: CpuRefRuntime`) so the run **counts** what it
claims: `grown == 0` and `accepted_begins == 0` of `begins == 1`. Both are asserted. Without
that wrapper this file would be a device-vs-device tautology — the R-8 class, one level up.

configuration, **not** shipped), tree 12 level 1:

```
assertion `left == right` failed: [buckets] tree 12: the CTR split sequence diverges between the device and CPU growers (full `CtrSplitSpec` identity: projection, ctr_type, prior_num, prior_denom, target_border_idx, border)
  left:  [CtrSig { projection: [0],    ctr_type: 0, prior_num: 0.5,  prior_denom: 1.0, target_border_idx: 0, border: 5.999999046325684 },
          CtrSig { projection: [0, 1], ctr_type: 1, prior_num: 0.25, prior_denom: 1.0, target_border_idx: 0, border: 11.999999046325684 }]
 right: [CtrSig { projection: [0],    ctr_type: 0, prior_num: 0.5,  prior_denom: 1.0, target_border_idx: 0, border: 5.999999046325684 },
          CtrSig { projection: [0, 1], ctr_type: 1, prior_num: 0.25, prior_denom: 1.0, target_border_idx: 1, border: 0.9999990463256836 }]
```

Same projection, same type, same prior; **`target_border_idx` 0 vs 1** with roughly
complementary thresholds (`bin > 11.99` vs `bin > 0.99`) — T10 §2's signature exactly. The
greedy search only diverges like this on an exact score tie, and an exact tie between two
columns means they induce the SAME partition on this data.

**Why the design choice did not prevent it, stated honestly.** A prior ≠ 0.5 removes the
exact algebraic mirror (`ctr(b0) + ctr(b1) = 1` becomes `(T + 0.5)/(T + 1)`, total-dependent)
but **not** the ordinal anti-monotonicity `bin(b0) + bin(b1) ≈ const`. With ~12 combination
buckets and 15 CTR bins, many threshold pairs still induce identical partitions and therefore
identical scores. **A prior ≠ 0.5 is necessary but not sufficient**; only the coordinator's
*other* option — a genuinely partition-invariant projection of the split set — is robust for
a long-horizon Buckets differential.

**Verified independent of D-2**: the identical failure, byte-for-byte, occurs with MUT-1 live
and with MUT-1 reverted (§4.1b). It is a property of the Buckets column pair, not of the
eligibility filter.

**Disposition**: the shipped Buckets arm is at rung 0 (5 iters), where the tie is not reached
and the raw comparison is exact across 5 trees with 3 combination splits. That is the ladder's
own "lowest rung that satisfies guard 4" discipline, not a search for a passing config — the
20-iteration run existed only as a MUT-1 probe. Recorded in full rather than quietly dropped.

## 7. Deviations from the task text

1. **The Counter arm ships at `iterations = 20`, not the fixture's 5** — guard-4 escalation
   ladder rung 1, the lowest value that satisfies assertion 4. Authorised explicitly by the
   task's escalation ladder; the full rung-by-rung measurement is in §3.3 and transcribed
   into the test's doc comment as the ladder requires. Guard 4 itself is untouched.
2. **The Buckets arm ships at `combinations_ctr_priors = [0.25]`, not `[0.5]`.** The task
   text specifies `vec![0.5]`; the coordinator's consolidated T10 §2 + T16 finding requires
   either a prior ≠ 0.5 for the Buckets arm or a partition-invariant comparison. The two
   documents conflict, the coordinator's is the later and more specific, and it was written
   *for this task*. Chosen up front and justified in the module doc (§1c), with the residual
   limitation recorded (§1d / §5.2). Counter and BTMV keep the task text's `0.5`.
3. **A second counting wrapper, `CountingCpu`.** `CountingGpu` is copied verbatim per GLOBALS
   §2.2.6 and is hard-typed to `inner: GpuBackend`, so the risk section's suggested "second
   `CountingGpu` wrapping `CpuRefRuntime`" cannot literally be that type. A sibling with the
   identical body and `inner: CpuRefRuntime` was added instead — preserving the verbatim copy
   rather than genericising it. It also counts `begin_device_training` calls and acceptances,
   so `accepted_begins == 0` is asserted alongside `grown == 0`.
4. **`simple_ctr`, `iterations` and `depth` are parameters of `diff_params`/`run`.** The task
   describes a fixed `combo_params()` with only `combinations_ctr` varying. `iterations` and
   `depth` are the ladder's rungs 1 and 2 and had to be per-arm; `simple_ctr` is a parameter
   only because the Counter ladder investigation drove it as a diagnostic (§3.3). **Every
   shipped arm passes `ECtrType::Borders`**, so the task's "simple_ctr stays Borders" holds
   for everything that ships, and the test asserts it per run.
5. **Four extra mutation runs beyond the two mandated**: MUT-1 was additionally driven at a
   longer horizon (§4.1b, to give it a real chance to discriminate, as the task demands), and
   MUT-2 was completed by the two complements MUT-2b/MUT-2c (§4.2, T18 §3's "drive the
   complement before deciding which diagnosis applies").
6. **One comment-only production edit** (`gpu_runtime/mod.rs`'s R-20 paragraph). The task's
   file list says "Production files: none expected" but its completion evidence requires "the
   R-20 comment in `mod.rs` updated to its measured status". Executable surface unchanged,
   proved by the identical `cb-backend` rocm figures.
7. **The `level_kinds` assertion canonicalises the documented optional encoding** rather than
   comparing raw vectors (§3.2), and adds a NEW assertion the raw comparison did not make (an
   empty vector must belong to a single-kind tree). Strictly stronger, not looser.
8. **`run_device_tests.sh` untouched** (C-8 — **T24** owns it). T22 adds ONE new binary,
