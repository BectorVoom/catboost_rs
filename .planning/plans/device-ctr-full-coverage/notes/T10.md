## 4. THE LEAF-GATHER FINDING — PLAN §6 assumption 8, SETTLED

### 4.1 Which path runs: **both**, and they are consistent by construction

| path | where | how it indexes the averaging CTR columns |
|---|---|---|
| the RETURNED leaf **VALUES** | `GpuTrainSession::grow_one`, `session.rs:2782-2839` (the `ctr_averaging_bins` arm) | **by CTR column POSITION** — `avg_bins.get(fu - base)`, `base = n_features - n_ctr` |
| the per-object leaf **ASSIGNMENT** that drives the main-approx update and the leaf weights | `boosting.rs:5589-5609`, the `device_has_ctr_split` branch of the oblivious device arm | **by FULL IDENTITY** — `assign_leaf_over_ctr_columns(&matrix, &averaging_ctr_features, &grown_like, n)`, whose `find` key is `projection && ctr_type && target_border_idx && prior_num.to_bits() && prior_denom.to_bits()` (`boosting.rs:2055-2062`) |

Note the second path exists on the device fit **because** `fused_unit_fold =
!device_has_ctr_split && …` (`boosting.rs:5511`) is `false` whenever a CTR split is present,
so the fused device-`leaf_of` fast path is structurally bypassed for CTR trees.

**Why the position-indexed device gather is CORRECT for the two-columns-per-`(projection,
prior)` Buckets layout** — i.e. why the failure mode the plan feared (a `b = 0` split paired
with the `b = 1` averaging column) cannot occur:

1. `materialize_ctr_columns_for_perm` (`boosting.rs:2203-2251`) is the **single** producer of
   both lists. It emits upstream's `(ctrIdx, targetBorderIdx, priorIdx)` nesting
   (`greedy_tensor_search.cpp:400-428`): `for target_border_idx in
   0..ctr_type.target_border_count(TARGET_CLASSES) { for prior in priors { … } }`.
2. `train_inner` calls it once with the **structure** permutation (`:4254`, kept as
   `materialized_ctr_features` at `:4272`) and once with the **averaging** permutation
   (`:4284-4295`), over the SAME `absolute_projections` / `ctr_candidates`. The two lists are
   therefore **index-aligned by construction, not by convention** — stated in-source at
   `:4282-4283` and in the function's own doc at `:2190-2193`.
3. `build_device_ctr_config`'s `build_columns` closure is an order-preserving `map` applied to
   each list (`:2592` structure, `:2594` averaging), and `ctr_covered` refuses any config with
   `avg.columns.len() != ctr.columns.len()` (`session.rs:189`).
4. ⇒ device CTR tail position `i` ⇔ `materialized_ctr_features[i]` ⇔
   `averaging_ctr_features[i]` — the SAME full identity, including `target_border_idx`.

And the host gather's full-identity `find` is correct — indeed **necessary** — for the same
layout: with two Buckets columns differing only in `target_border_idx`, a
projection-and-type-only key would return the `b = 0` column for a `b = 1` split. The
`target_border_idx` conjunct at `:2059` is exactly what prevents that (measured: §4.2 MUT-C).

**No mismatch. Nothing to escalate. No patch to the gather was made or needed.**

### 4.3 The `[0,1,0,0,1,1,0,1]` (CPU) vs `[0,0,0,0,0,0,0,0]` (device) selector difference

Both runs reproduce upstream at `max |Δpred| = 2.776e-17`, so the two models are
prediction-equivalent. The reason is an **exact mirror symmetry at `Prior = 0.5`**:

```
ctr_b        = (counts[b] + prior) / (total + 1)          (online, read-before-increment)
counts[0] + counts[1] = total                              (binclf, SIMPLE_CLASSES_COUNT == 2)
⇒ ctr_0 + ctr_1 = (total + 2·0.5) / (total + 1) = 1        EXACTLY, for every object
```

`calc_normalization(0.5) = (shift 0, norm 1)`, so both columns binarize over `[0, 1]` into
the same 15-border table and their bins are mirrored. A split `bin(b=0) > k` is therefore the
**complement** of `bin(b=1) > 14−k`, and a complement split is the same partition with that
level's bit flipped — the same oblivious tree modulo a leaf permutation, hence identical
predictions. Which member of the mirror pair wins is a strict-`>` / first-wins scan-order
artifact between the CPU and device scorers, not a semantic difference.

Sanity check on that reading: a genuine structural divergence on this class of fixture looks
like FPP-11's `3.3e-2` or MUT-A's `2.5e-1`, not `2.776e-17`.

**Two consequences later tasks must carry** (also appended to COORDINATOR-FINDINGS):

1. The device path never *selects* a `Buckets@1` split here, so this e2e does **not** exercise
   the `b = 1` numerator through the SCORING path. Its `b = 1` evidence is (a) T08's kernel
   self-oracle and (b) MUT-A. Do not read "the Buckets e2e is green" as "b=1 scoring is proven".
2. T20's heuristic *"an unexpectedly tiny `max |Δpred|` is a CPU-fallback smell"* has a
   **counterexample** here: the device and CPU paths print the **same** `2.776e-17`. The
   discriminators that still worked were `grown == 5` and the runtime (1.7 s vs 0.01 s).
