## 1. Which layer each sub-case declines at (the coordinator's explicit question)

**Both declining cells decline at `device_host_eligible`'s `&& eval_sets.is_empty()` conjunct
(`crates/cb-train/src/boosting.rs:4620` at the time of writing — locate by clause text, the
line drifts), NOT at the `ctr_type` conjunct of `ctr_types_are_device_covered`.**

T12's warning is fully honoured: since DCTR-10 the CTR type list admits `Counter`, so a T13
negative that leaves `eval_sets` empty would decline for **no** reason and pass vacuously.
Three independent things pin the layer:

1. **Structural**: `Full`'s only effect in this crate is `counter_full_eval_columns`,
   assembled purely out of `eval_sets` (`boosting.rs:4231-4249`) and collapsing to
   `Vec::new()` through its `cols.iter().all(Vec::is_empty)` arm when there are none ⇒ with
   an empty eval-set slice **`Full ≡ SkipTest`**. Consumed downstream as
   `materialize_ctr_feature`'s `extra_cat_columns` → `online_counter_column`'s `extra_bins`.
2. **Test side** (the square above): the `Full`/no-eval cell **commits**, so `Full` is not a
   declining factor; the `SkipTest`/eval cell **declines**, so the eval set alone is.
3. **Production side** (MUT-1, §3.1): deleting *only* `&& eval_sets.is_empty()` flips **both**
   declining cells to `grown = 5` and leaves both committing cells green. Nothing else in the
   conjunction is holding those two fits off the device.

Complementarily, MUT-2 (§3.2, T20's universal `&& false` on the CTR type gate) reddens **only
the two committing cells**. So the two mutations partition the four cells exactly: the type
gate governs the commits, the eval-set clause governs the declines. A `grown == 0` assertion
on its own cannot tell those two layers apart — that is why both mutations were run.

**C-1 applied**: all four cells train through `train_cat_with_eval_sets`
(`boosting.rs:3110-3121`) with a real `&[EvalSet]` (`boosting.rs:2691-2703`, located by
symbol — T02/T10/T12 shifted the file). `train_cat`'s sixth argument is `weights`, and a test
written against it would assert on a structurally-empty eval-set list. The test additionally
asserts `eval_sets.is_empty() == !with_eval_set` in-test, so a cell that *thinks* it passed an
eval set but did not fails loudly rather than silently becoming the vacuous C-1 case.

## 5. Deviations from the task text

1. **The LEARN side is the WHOLE 64-row fixture, not a 32-row half; only the EVAL side is a
   half (rows 32..).** Forced by measurement — §3.0's verbatim failure: a 32-row learn half
   produces **zero CTR splits** in three of the four cells, making the pin vacuous. The
   replacement is strictly stronger for the task's purpose: the learn set is now
   byte-identical to DCTR-10's, i.e. the exact configuration `device_ctr_counter_fit_test`
   already proved commits with 5 Counter splits at `1.388e-17`, so the *only* structural
   difference between a committing and a declining cell is the eval-set slice. The eval rows
   overlap the learn rows; that is immaterial because **nothing in this file compares
   predictions or metrics** — the eval set's entire role is to be genuinely non-empty and to
   carry the categorical column `Full` would widen the tally with (both asserted in-test).
   Recorded in-source on `EVAL_HALF_START` so the next reader does not "restore" the split.
2. **Four cells, not two.** The task's two cells differ in *two* factors at once and so cannot
   localise the decline; T12's finding #1 makes localisation the whole point of this task. The
   square adds `counter_skiptest_with_eval_set_declines_to_cpu` and
   `counter_full_without_eval_set_commits`. Both required names are present and unchanged.
3. **Two mutations, not one.** MUT-1 is the task's specified mutation and covers the two
   declining cells; the two *committing* cells are also green-on-write and §2.5 applies to
   them too, so MUT-2 (T20's universal `&& false`) was run for them. Together they partition
   the four cells and are what turn "declines at the eval-set layer" into a measurement.
4. **A production doc edit, in a task whose Files/symbols block says "Production files:
   none".** The task's own Refactor step orders it ("Add the same note to
   `ctr_types_are_device_covered`'s doc block"), so the block is resolved in favour of the
   explicit instruction. It is **doc-only** — proven by `git diff`: every added non-comment
   line in `boosting.rs` is T12's.
5. **`run_device_tests.sh` NOT touched** (C-8: T23 owns it). The new binary
   `device_ctr_type_gate_test` was verified with explicit `--test` invocations, and T23 must
   add it to `TESTS=(…)`.
