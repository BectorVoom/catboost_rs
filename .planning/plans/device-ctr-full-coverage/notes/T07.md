### Non-vacuity probe for the discriminating assertion (read-only, no writes to `fixtures/`)

Ran the generator's own `make_data(0)` + `fit` in the scratchpad against three CTR types:

```
BinarizedTargetMeanValue:Prior=0.5 -> n_descriptors=1  types=['BinarizedTargetMeanValue']  tbi=[0]
Buckets:Prior=0.5                  -> n_descriptors=1  types=['Buckets']                   tbi=[0]
Borders:Prior=0.5                  -> n_descriptors=1  types=['Borders']                   tbi=[0]
```

**Finding worth carrying forward (affects T05):** `model.json`'s `ctrs` array is the
**used/pruned** descriptor set, so on *this* data shape even `Buckets` yields a single
entry with `target_border_idx = 0`. Consequently the `len(ctrs) == 1` count alone does
**not** discriminate BTMV from Buckets here — what discriminates is the
`ctrs[0]["ctr_type"] == "BinarizedTargetMeanValue"` assertion, which flips cleanly with
the recipe (shown above). Both assertions are in the generator **and** the smoke test.
T05's `target_border_idx ∈ {0,1}` guard reads the same pruned array, which is direct
evidence for that task's escalation ladder being necessary rather than optional.

No §2.5 mutation check was required: T07 is not in the plan's nine-item mutation-candidate
list, and the test was genuinely **RED before / GREEN after** rather than green-on-write.

## Deviations

1. **The corpus-contamination check exits 1 on the two sibling fixtures.** Kept verbatim
   from the combo generator as T05 mandates. Its `git status --porcelain <fixtures>` scan
   reported
   `?? crates/cb-oracle/fixtures/ctr_device_buckets/` and
   `?? crates/cb-oracle/fixtures/ctr_device_counter/`
   as offenders. Those are **T05's and T06's directories, created concurrently by other
   agents** — not paths this generator touched. Every artifact of this fixture was written
   before that check runs, and all anti-false-pass assertions had already passed. The
   check itself was **not** modified (whitelisting siblings would have deviated from the
   "verbatim" instruction). Anyone re-running this generator on a clean tree will see it
   exit 0.
2. **`catboost_info/` removed after generation.** Running the generator with cwd inside
   the fixture directory makes CatBoost drop a `catboost_info/` training-log directory
   there. `.gitignore` only covers `crates/cb-oracle/{generator/,}catboost_info/` and a
   root-level `/catboost_info/`, so this copy would otherwise have been committed. It is a
   training log, not fixture data, and no sibling fixture ships one; it was deleted.
3. **`X_cat.npy` is 1-D `[64] int32`, not `[64,1]`.** `CARDS = (6,)` is a single cat
   column, and both the shipped single-cat precedent (`ctr_device_mixed/X_cat.npy`,
   `(64,) int32`) and the downstream consumer contract (T10's Red says `X_cat.npy` `[N]`
   int32; T16 inherits it) call for the flat form. The combo generator's
   `np.stack(..., axis=1)` is retained for the data build and the column is flattened at
   save time, with a comment saying why.
4. **`escalation_rung: 0`.** T07 carries no escalation ladder of its own (that is T05's);
   the base recipe passed at the first seed, so the field is recorded as 0 for symmetry
   with the sibling fixtures.
