### C-17 honoured

The `norm == 0.0` guard is **not** added. The new comment block states explicitly that
`calc_ctr_online_bin`'s guard (`calc_ctr.rs:97-99`) is **dead code** — `calc_normalization`
returns `norm = max(1, p) - min(0, p) >= 1` for every `p` — and is deliberately not
mirrored. It is nowhere presented as a live safety check.

### Coordinator finding from T03 acted on

All float comparisons in the new test use `assert_eq!` (IEEE `PartialEq`), never
`f64::to_bits`. The test's own `calc_normalization(2.0) == (0.0, 2.0)` derivation
assertion is a `PartialEq` compare for exactly that reason, and the module header records
why (`shift = -min(0, p)` ⇒ `-0.0` at `p = 0`).

**No widening was needed to reach the predicted state.** The two-document construction
(one cat column `["a","a"]`, identity permutation `[0, 1]`, classes `[1, 0]`,
`prior = 2.0/1.0`, `ctr_border_count = 15`) put document 1 on the
`(good = 1.0f32, total = 1)` prefix exactly as predicted, and the assertion was **never**
weakened to the clamped value. The by-construction witnesses
(`ctr_value[0] == 2.0`, `ctr_value[1] == 1.5` — the raw `calc_ctr_online` prefix value,
which DCTR-04 does not touch) passed on the very first Red run, proving the state was
reached rather than assumed.

**The column was nevertheless widened to THREE documents afterwards, to strengthen — never
to weaken — the assertion.** See the deviation section below: the plan's two-document
construction cannot discriminate the `norm`/`denom` conflation that the refactor half of
this task exists to prevent. Document 2 (classes `[1, 0, 0]` ⇒ it reads
`sum = 1.0, count = 2` ⇒ `ctr = 1.0`) separates all three candidate implementations:

## Deviations from the plan

1. **The Red column was widened from two documents to three — to STRENGTHEN, not weaken.**
   The plan's two-document construction reached the predicted `(good = 1.0, total = 1)`
   state on the first try and produced the predicted `left: 15, right: 11`. But mutation
   M2 shows it is **blind to the `norm`/`denom` conflation**: at `count = 1` the CTR
   denominator (`1 + 1 = 2`) coincides numerically with `calc_normalization(2.0)`'s
   `norm = 2.0`, so documents 0 and 1 both pass under the conflated implementation. Since
   clearing exactly that shadowing trap is the stated purpose of this task's Refactor
   step, a third document (`ctr = 1.0` ⇒ correct 7, uncorrected 15, conflated 5) was added.
   No assertion was weakened; the plan's document-1 assertion is retained verbatim.
2. **Mutation-check applicability.** §2.5 mandates mutation checks for *green-on-write*
   tests; this test went Red→Green, which is strictly stronger. Both mutations were run
   anyway — M1 because it re-establishes the Red against the *final* (widened) test, M2
   because it is the only evidence that the widening was necessary.
3. **`planning/settings.json`, not `.planning/settings.json`** (no leading dot), as T03
   already recorded. Read and honoured: `implementation.use_worktree = false`.
4. **Concurrent T01 edits were present in the tree** and were not touched:
   `crates/cb-train/src/boosting.rs`, `crates/cb-train/src/device_ctr_combo_config_test.rs`,
   the new `crates/cb-train/src/boosting_ctr_gate_test.rs`, plus T01's own note and its
   COORDINATOR-FINDINGS entry. Every `cb-train` command above compiled **including** those
   in-flight changes and passed.
5. **The pre-existing `cargo clippy -p cb-train --lib --tests` failure is broader than
   recorded** — 12 integration-test targets, not just `device_seam_test.rs`. Recorded here,
   not fixed (out of T04 scope; T24 owns it).
