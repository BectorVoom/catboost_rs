## 3. The §2.5 judgement call — **MUTATION, not the substitute**

**PLAN §2.5 lists T15 explicitly "per the checker's judgement request" and offers the `>= 2 distinct
bins` guard as an accepted substitute for a full mutation. I did NOT take the substitute. Two real
production mutations were run.**

### 3.1 Why a mutation was both possible and necessary here

The substitute was offered on the reasoning that (a) the test is green by construction and (b)
T14's own detector-B mutation already proves the accumulator discriminates. Both are true, and
neither covers **the vacuity mode specific to a differential**: an equality between two columns is
also satisfied when the two columns are *the same column*. The guard cannot see that. Concretely,
had the test called `binarize_btmv_column_host` twice (a plausible copy-paste), or
`binarize_ctr_column_host` twice, it would be green, would have ≥2 distinct bins, would satisfy
T04's occupancy guard — and would assert **nothing**. That is precisely T14's MUT-C failure mode
transposed: *a green test whose green comes from somewhere other than the claimed property.*

A mutation of **one** arm discriminates that mode completely, in both directions:

* if the test secretly compared BTMV with BTMV, a BTMV-only mutation moves **both** sides equally
  and the test stays **green**;
* if it secretly compared Borders with Borders, a BTMV-only mutation moves **neither** side and the
  test stays **green**.

So a BTMV-only mutation that turns the test **red** is a proof that the two arms are genuinely
distinct, genuinely live, and that the equality is a statement about the equivalence rather than
about an accident of the fixture. That is exactly the discrimination DCTR-13 claims, and it costs
one line and ~30 seconds. **When a real mutation that discriminates the claimed equivalence exists
and is cheap, taking the substitute would be a choice to know less for no reason.**

### 3.2 What the `>= 2 distinct bins` guard *does* cover, and what it does not

It is still in the test (and is asserted on the **reference** column deliberately — the side no
BTMV-side mutation can move, so it can never be the thing that fires under §2.5 and mask the
equality failure). It covers exactly one thing: a degenerate all-one-value column, against which any
equality is trivially satisfiable. Measured on this fixture the reference column has **11 distinct
bins** (printed by both mutation failures below), so the guard passes with a wide margin.

What it would **fail to catch**, and what the mutations therefore had to catch instead:

1. **A self-comparison** (either arm duplicated) — non-degenerate and green.
2. **A wrong-but-consistent reference arm.** If `binarize_ctr_column_host` were routed at
   `(Buckets, 0)` rather than `(Borders, 0)`, the test's *name and claim* would be false while the
   column stayed perfectly non-degenerate. MUT-2 is aimed exactly at this.
3. **A border table too coarse to resolve a real divergence.** ≥2 distinct bins says the column
   varies; it does not say the binarization can *see* a numerator error. MUT-1's answer — all 128
   documents differ — settles that empirically.

### 3.3 MUT-1 — the BTMV accumulator folds the COMPLEMENT class (`Sum = N[0]`, not `N[1]`)

`crates/cb-backend/src/kernels/ctr_device.rs:386`, inside `btmv_ctr_prefix_kernel`:

```rust
-  sums[bucket] = s + (f32::cast_from(class[doc]) / dv);
+  sums[bucket] = s + ((dv - f32::cast_from(class[doc])) / dv);
```

At `divisor = 1` this makes `Sum` the count of class-**0** documents — i.e. it aliases BTMV onto the
**Buckets@0** numerator instead of the **Borders@0** one. Chosen over a cruder break (zeroing the
accumulator, hoisting the write) because it is the *semantically adjacent* error: the statistic is
still a legitimate class prefix, still non-degenerate, still in `[0,1]`, and only the **direction**
of the claimed equivalence is wrong. That is the failure DCTR-13 exists to exclude.

### 3.5 T14's MUT-C hazard — checked, does not apply

T14 recorded that a mutation can PASS because a **sibling guard** rejects the input first, leaving a
silently vacuous test. That hazard is specific to *negative* tests with an ordered chain of
rejecting guards. This test is positive: its guards are non-vacuity assertions, not rejectors, and
they are ordered so that the equality — the assertion under test — is the **last** thing evaluated
(and guard (c) is asserted on the arm no mutation moves, §3.2). Both mutations failed on their
**first** run, at the equality, with the intended payload; neither was masked, and neither required
the input to be strengthened. Recorded here because the check was made, not assumed.

## 4. Non-vacuity, asserted rather than assumed

**T04's ≥3-documents constraint (mandated by the coordinator, inherited via T14 finding 4):
SATISFIED with a wide margin, and enforced at runtime.** `max_bucket_occupancy(&bins) >= 3` is
asserted in the test. Measured on `synth_fixture(128, 5, 3)` (recomputed independently from the LCG):

```
bucket occupancy: {0: 32, 1: 19, 2: 24, 3: 28, 4: 25}   max = 32, min = 19
class counts:     {0: 63, 1: 65}
```

Every one of the five buckets holds **19–32** documents, so the oracle drives `count` far past the
`count == 1` point at which `calc_normalization`'s `norm` and the CTR denominator (`total + 1`)
coincide — the blind spot T04 measured and the reason the construction had to be widened past two
documents. `BTMV_DIVISOR_BINCLF = 1` is used, as T14 §8 requires: the equivalence is a binclf-only
identity and is simply false at `divisor = 3`.

Three guards in total:

* **(a)** `max_bucket_occupancy(&bins) >= 3` — T04's dial (measured 32).
* **(b)** both classes occur — on an all-zero class column `Sum ≡ 0`, on an all-one column
  `Sum ≡ Count`; either way the two paths would coincide for a reason unrelated to the claim
  (measured 63 / 65).
* **(c)** the reference column has `>= 2` distinct bins — PLAN §2.5's named guard (measured **11**).
