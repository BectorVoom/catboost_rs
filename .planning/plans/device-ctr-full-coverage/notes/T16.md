## 4. What this oracle can and cannot police (MATERIAL — carried to COORDINATOR-FINDINGS)

T15 measured that at binclf the device BTMV column and the device `Borders@0` column emit
**identical cindex bins**, on all 128 documents of its fixture. That identity is exact, not
approximate (`Sum == N[1]`, `Count == Total` when the addend is `targetClass / 1 ∈ {0,1}`).

⇒ **the ≤1e-5 bar in this e2e cannot distinguish BTMV routing from Borders routing.** A device
path that kept sending these columns through `launch_ordered_ctr_resident` at
`(CTR_TYPE_BORDERS, 0)` would produce identical predictions and pass. This is a *different* blind
spot from T06's Counter-prior one (which was fixture-specific); this one is **structural and
holds for every binclf BTMV fixture**, so no fixture choice could have closed it.

Three layers close it instead, none of which depends on the predictions:

1. **the per-split `ctr_type` assertion** in the e2e (every chosen CTR split must carry
   `BinarizedTargetMeanValue`) — this is the assertion that would fail if the materialization
   emitted Borders columns;
2. **the launchers' incompatible signatures** — `launch_btmv_ctr_resident` takes a `divisor` and
   no `(ctr_type, target_border_idx)`, and returns a `ResidentCtrMean`; the ordered launcher is
   the reverse and additionally *rejects* `ctr_type == 2`. A routing swap is a compile error, and
   MUT-6 shows the arm is genuinely on the path;
3. **DCTR-12's kernel self-oracle** proves the accumulator against the CPU `online_mean_prefix`
   independently of any fit.

The e2e's module doc and the gate's doc block both state this in-source so a later reader does
not treat the green bar as routing evidence.

**T04's ≥3-documents constraint is satisfied and enforced**: `max_bucket_occupancy(X_cat) >= 3`
is asserted at runtime and measures **15** on the frozen fixture (64 rows over cardinality 6),
far past the `count == 1` point where `calc_normalization`'s `norm` and the CTR denominator
`total + 1` coincide.

**The frozen fixture was never opened for writing** — `git status --short crates/cb-oracle` is
empty; `crates/cb-oracle/fixtures/ctr_device_btmv/` is byte-untouched (§2.6), and its smoke test
re-runs green.

## 6. Deviations from the task text

1. **A THIRD gate test, `the_admitted_set_is_exactly_the_cpu_supported_types`.** The task text
   specifies the widening only. But T16 is the task that CLOSES the type track, and the file's
   extension contract asks for the structural reason a change is safe — here the reason is a
   *partition*: `is_cpu_supported()` splits `ECtrType` into exactly the admitted four and the two
   GPU-only types. Without this pin, a later task could widen past that partition (claiming a
   parity surface upstream does not provide) and no test would notice: the gate-state table only
   covers the shapes it enumerates. One test, no production change, mutation-proved by MUT-1.
2. **`buckets_keeps_the_borders_shape_checks` (T09's test) gained
   `BINARIZED_TARGET_MEAN_VALUE`.** Same reasoning and same precedent as T12's deviation 1 (C-7:
   admitting a type changes nothing else). BTMV is the type with the *strongest* case for the
   addition, since it is the one whose CPU quantizer is the `quantize_in_f32` arm. Mutation-proved
   (§3.4). The test name was deliberately not changed.
3. **A named const `UNKNOWN_DISCRIMINANT: i8 = 6` for the mixed pair**, rather than a bare `6`.
   T12 said "an out-of-enum stray (e.g. `6`)"; naming it lets the in-source note explain *why* a
   stray is now the durable choice. Mutation-proved (§3.5).
4. **`build_ctr_cindex_columns`' `match` binds `value: Handle`, not a `res` struct.** Forced:
   `launch_btmv_ctr_resident` returns `ResidentCtrMean` and the other two return `ResidentCtr`,
   which are different types, so a common binding is impossible. Binding only the shared f64
   `value` channel is the minimal restructure and it makes C-7 visually obvious (the binarize
   below cannot see the type at all). No behaviour change for Borders/Buckets/Counter — proved by
   the three unchanged D-04 numbers.
5. **`BTMV_DIVISOR_BINCLF: u32 = 1` is a named const in `ctr_device.rs`, not a literal
   `1` / `1.0f32` in `session.rs`.** The task text says `divisor = 1.0f32`; the launcher's host
   parameter is `u32` (T14 deviation 4 — that is what makes its `class <= divisor` guard exact),
   and it crosses the seam as f32 internally. Spelling the value once, next to the discriminant
   consts and with the `SIMPLE_CLASSES_COUNT` citation, follows the same C-3 discipline the task
   applies to `CTR_TYPE_BTMV`.
6. **The e2e asserts its own prior pin and its own bucket-occupancy dial**, which the task does
   not enumerate. The prior pin mirrors T12's deviation 4 (the trap here is the opposite shape —
   three default priors instead of one). The occupancy assertion is the coordinator's explicit
   ≥3-documents instruction, made executable rather than left to review.
7. **Seven mutations, not the minimum.** MUT-1/2/3 are the mandatory §2.5 set for the two
   green-on-write gate pins plus the row-5 isolation; MUT-4 covers deviation 2; MUT-5 covers
   deviation 3 (and answers T14 §5's "does the swapped operand still discriminate?"); MUT-6 is
   the routing proof described in §3.6; MUT-7 is T20's universal check re-run post-Green to prove
   no residue.
8. **The backend-side Red (§2.2) was RE-CREATED, not observed in flight.** The production
